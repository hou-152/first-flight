# Create Website Brief

帮用户产出 `BRIEF.md`——一份 200-400 字的网站项目**长期纲领**，回答"这是什么 / 给谁 / 解决什么 / 长期成功是什么 / 本质边界在哪"五个核心问题。这是用户和 AI 协作开发网站的第一份上下文文档。

## 这个 skill 解决的问题

很多想做网站的人卡在"不知道怎么和 AI 讲清楚我要什么"。直接让 AI 写代码，得到的是泛泛的模板站；先写 BRIEF，则后续 PRD / DESIGN / ARCHITECTURE 都有锚点。

**BRIEF 是长期纲领，不是 PRD**：
- BRIEF 描述项目**永久不变**的部分——定位、目标用户、核心价值、本质边界。一份 BRIEF 在项目生命周期里基本只写一次，偶尔微调。
- PRD 描述**这一次迭代**要做的功能、页面、KPI、上线指标。每一次新版本可能对应一份新 PRD。
- 所以 BRIEF 里**不要写 MVP 范围、不要写本次要上线的功能清单、不要写短期 KPI**。这些都属于 PRD。

控制在 200-400 字是刻意的：太长会侵入 PRD 的领地，太短会留下后续无法回答的歧义。这个字数刚好能逼用户做出"取舍"。

## 整体流程

```
[Step 0] 识别用户经验度 → 分流到路径 A（小白）或路径 B（有经验）
   ↓
[Step 1] 项目概况：这是什么 / 给谁 / 在什么场景下用
   ↓
[Step 2] 价值与成功：解决什么问题 / 成功长什么样
   ↓
[Step 3] 范围与边界：做什么 / 不做什么 / 关键约束
   ↓
[Step 4] 综合回答 → 生成 BRIEF.md → 让用户确认 → 写文件
```

每个 Step 1-3 用一次 `AskUserQuestion`（如果可用）打包 3-5 个相关问题，节奏快但不轰炸。Step 0 单独问一次。

## Step 0：识别经验度 + 分流

第一件事是判断用户的经验度，因为同一个问题对小白和有经验的人，措辞和选项粒度差别很大。

用一次 `AskUserQuestion` 问：

> 为了用合适的节奏引导你，你对"做网站 / 和 AI 协作开发"的熟悉度是？

提供这 4 个选项（选项里加示例帮用户对号入座）：

1. **完全新手**——只知道想做个网站，没接触过开发，分不清前端后端 → 走路径 A
2. **看过一些教程，但没自己做过** → 走路径 A
3. **是产品 / 设计 / 创业者**——知道目标用户、MVP 这些概念，只是不写代码 → 走路径 B
4. **是开发者 / 有过协作开发经验** → 走路径 B

记住选择，后面所有问题按对应路径走。

## 两条路径的差异原则

**路径 A（小白）的提问要求：**

- 用大白话，不出现"目标用户、KPI、MVP、范围、约束"这种产品/工程术语
- 每个问题必须给 3-4 个具体选项 + "其他（我来描述）"
- 每个选项后面带 1 个生活化的例子，让用户能对号入座
- 例：与其问"你的目标用户是谁"，问"这个网站主要是给谁看的？"，选项里给"主要给我自己的朋友 / 同行看（比如展示作品的）"、"给可能想买我产品 / 服务的人看"等

**路径 B（有经验）的提问要求：**

- 可以直接用产品 / 工程语言
- 选项更精炼，允许"其他"自填
- 节奏更快，必要时允许多选

两条路径的"问的本质"是同一个，只是表达方式不同。下面列每一步要问到的"本质信息"，由你按路径调整措辞。

## Step 1：项目概况

要问到的 3 件事：

1. **网站类型**——它是个什么形态的网站？
   - 路径 A 选项示例：个人作品集（展示我做过的东西） / 个人博客（写文章） / 公司官网（介绍公司 + 产品） / 产品落地页（卖一个具体产品 / 服务） / 工具型网站（用户来用一个功能，比如计算器、转换器）/ 其他
   - 路径 B 直接列：portfolio / blog / corporate / landing page / SaaS app / tool / community / 其他
2. **谁会来这个网站**——主要受众
   - A：让用户描述场景，比如"会来找工作的 HR"、"想买我做的小程序的开发者"
   - B：可以直接问目标用户画像 + 来访场景
3. **网站名字 / 项目代号**（如果还没想好，先用占位符）

## Step 2：价值与长期成功

要问到的 2 件事：

1. **核心问题 / 价值主张**——为什么用户要看 / 用这个网站？没有它会损失什么？
   - A：可以反向问"如果用户从这个网站离开时只记得一件事，你希望是什么？"
   - B：直接问 value proposition / 核心问题
2. **长期成功的样子**——网站长期跑顺以后，扮演的是什么角色？1 年以上的时间尺度里希望它达成什么？
   - 注意：这里**不要问短期 KPI**（如"3 个月内拿到多少咨询"）。短期指标属于 PRD。
   - 这里要拿到的是**长期定位**——可以是一种状态、一种角色，或者 1 年以上的累积成果
   - A 选项示例：成为我接客户 / 找工作时拿得出手的第一名片 / 成为我领域内被同行认可的内容来源 / 成为公司的主要获客入口 / 还没想清楚，先做出来再说
   - B 直接让用户描述长期定位

## Step 3：本质边界

要问到的 2 件事（注意：这一步问的是**永久性**边界，不是某一版要做什么）：

1. **本质上永远会是什么**——这个项目的根本性质，哪怕过 3 年也不会变
   - 例如："永远是一个作品集站，不会扩展成商城" / "永远是 SaaS 产品的官网，不会变成博客平台" / "永远只服务 B 端客户，不会做 C 端"
   - 关键词或短句即可
2. **永远不会做的方向**——从一开始就明确排除，未来即便有人提，也不会往这个方向扩
   - 这一项是 BRIEF 最重要的"防漂移"机制。常见的"诱惑性方向"：加用户系统、做社区、做电商、做多语言、做 mobile app
   - 如果用户说"都想做"，提示他："凡是不是项目本质的部分，写到永远不做里。等真的要做时，那就是另一个项目了"

**不要在这一步问"这一版做什么页面 / 功能"**。如果用户主动列功能清单，告诉他："这些先放着，我们后面会写 PRD.md，专门承接每一次迭代要做的页面和功能。BRIEF 只管纲领。"

## Step 4：综合回答 → 生成 BRIEF.md

把所有回答整合，按下面的固定模板写。**严格控制在 200-400 字**（中文字符，不含模板标题）。如果超过 400 字，自己删减；如果不到 200 字，向用户追问 1-2 个最薄弱的点。

### BRIEF.md 模板

```markdown
# {项目名} · BRIEF

## 一句话定义
{用一句话讲清楚：网站类型 + 给谁 + 解决什么。30-50 字。}

## 目标用户
{画像 + 来访场景。回答"什么样的人，在什么情况下，会打开这个网站"。50-80 字。}

## 核心价值
{用户为什么要看 / 用这个网站。没有它会损失什么。强调差异化或独特角度。50-80 字。}

## 长期成功的样子
{长期跑顺以后，这个网站扮演什么角色 / 达成什么状态。可以是定性描述，也可以是 1 年以上时间尺度的成果。50-80 字。}

## 本质边界
**永远会是的：** {项目的根本定位，3 个关键词或短句}

**永远不会做的：** {从一开始就排除的方向，3 个关键词或短句}
```

> **重要约定**：BRIEF 是项目级别的长期文档。"这一版要做哪些页面 / 功能 / 短期 KPI" 这些**不要**写进来——它们属于 PRD。BRIEF 应该是一份哪怕过两年还基本成立的文档。

写完后**先在对话里展示给用户预览**，问："这份 BRIEF 看着对吗？需要改哪里？"。改完再写文件。

### 写文件

默认写到当前工作目录下的 `BRIEF.md`。如果当前目录已经有同名文件，先读一下、给用户对比、再确认是否覆盖。如果用户的会话环境是 Cowork，写到 outputs 目录下并给出 `computer://` 链接。

## 写作风格守则（用于生成 BRIEF.md 时）

- 用陈述句，不用"将会、可能、希望"这种弱化语气
- 不要堆砌形容词（"美观、专业、现代"这类不携带信息）
- 名词具体——"独立开发者"比"用户"好，"成为我接客户时拿得出手的第一名片"比"获得用户"好
- BRIEF 是给"未来的 AI 协作伙伴"看的，所以**所有歧义都要消除**，不要留"等做的时候再定"
- 如果回答里出现了"页面 / 功能 / 按钮 / 首版 / MVP"这种 PRD 层面的细节，**不要放进 BRIEF**，告诉用户这些会在 PRD 里承接

## 结束语

写完文件后告诉用户：

> BRIEF.md 已生成。First Flight 的下一步是 PRD.md——把这份长期纲领落实成第一版要做的具体页面 / 信息架构 / 目标。完整流程剩 5 步：PRD → DESIGN（视觉风格）→ ARCHITECTURE（技术选型）→ CONTENT（内容填充）→ AGENTS（把所有文档串起来给 AI 用）。
>
> 现在就接着做 PRD 吗？

如果用户同意，立即切换到 `first-flight-prd` skill 接着走。如果用户想停一下，尊重——First Flight 的设计原则是每一步完成后由用户决定是否继续。
