# First Flight · PRD

帮用户产出 PRD.md——把项目的长期纲领落实成"这一次迭代要做的所有页面、信息架构、目标衡量"。

**首次和迭代都用这个 skill**，行为按检测结果分支：
- **首次**（项目还没 iterations/ 目录）：从 BRIEF 落地到第一版 PRD，写到 `iterations/v1-launch/PRD.md`
- **迭代**（项目已有 iterations/v1+/）：基于 BRIEF + 上一次 PRD 写新一轮 PRD，写到 `iterations/v{N}-{slug}/PRD.md`

## 与其他文档的分界（先读）

- **BRIEF.md**（项目根，长期）——项目长期纲领。PRD **不重复** BRIEF 的内容，只在"项目背景"指向回 BRIEF。
- **PRD**（本 skill 输出，归属某次迭代）——本次迭代要做的：用户与场景、页面结构、信息架构、目标衡量、范围、风险。
- **CONTENT.md**（仅首次生成，在 iterations/v1-launch/）——具体填进每个内容槽的文案 / 数据源。**迭代时不再生成**（内容由 CMS / JSON / API 管理）。
- **DESIGN.md**（项目根，长期）——颜色、字体、组件视觉。PRD **不写**这些。
- **ARCHITECTURE.md**（项目根，长期）——技术栈。PRD **不写**这些。
- **PRD 写**：功能行为 + 信息架构（每个区块的"用途和内容槽清单"）。"slogan 区放一句话和一个 CTA"OK；"按钮用 #007AFF"不 OK；"用 Next.js 部署"不 OK。

## 整体流程

```
Step 0a  读 BRIEF.md（必读）→ 找不到则建议先做 BRIEF
Step 0b  检测 iterations/ → 决定首次 or 迭代分支
   ↓
Step 1   识别用户经验度 → 路径 A（大白话）或路径 B（直接、可用术语）
   ↓
Step 2   分批问问题（4 批，迭代时第 1 批不同）
   ↓
Step 3   skill 预填"风险与待解决问题"的常见项，让用户补充
   ↓
Step 4   预览 PRD → 用户确认 → 写到对应 iterations/v{N}-{slug}/PRD.md
```

## Step 0a：读 BRIEF.md

去项目根读 `./BRIEF.md`：

1. **找到了**：简短复述："我看到 BRIEF 是 [项目名]，定位是 [一句话定义]。"
2. **没找到**：告诉用户："PRD 需要先有 BRIEF 作为长期纲领。建议先用 first-flight-brief 产出 BRIEF.md。要不要先做？"

## Step 0b：检测首次 vs 迭代

**这一步决定 skill 的分支和写入路径**：

1. 检查 `./iterations/` 目录是否存在
2. 如不存在 / 为空 → **首次分支**，目标路径 `iterations/v1-launch/PRD.md`
3. 如存在且有 `v?-*/` 子目录 → **迭代分支**：
   - 列出现有迭代（如 `v1-launch/`、`v2-blog/`）
   - 找最高 N，本次默认 N+1
   - 问用户："看到你已经有 [v1-launch, v2-blog]，本次迭代是 v3——叫什么 slug？（如 `checkout-redesign` / `i18n` / `dark-mode`）"
   - 收到 slug 后，本次目标路径 `iterations/v{N+1}-{slug}/PRD.md`
4. **用户压过自动检测**：用户明说"这是首次"（即使 iterations/ 存在）→ 警告"会创建在 iterations/v1-launch/，可能覆盖已有 v1"后按首次走

**迭代分支额外读上一份 PRD**：找最新的 `iterations/v{N}/PRD.md`（N 是当前最高 - 1）作为"上一版起点"读进来。
   - 如果用户坚持继续，照常进行，但在 PRD 末尾备注"BRIEF 缺失，建议补做"。

## Step 1：识别经验度

用一次 `AskUserQuestion`：

> 为了用合适的节奏走，你对"和 AI 协作开发产品"的熟悉度是？

4 个选项（与 create-website-brief 一致）：

1. **完全新手** → 路径 A
2. **看过教程，没自己做过** → 路径 A
3. **是产品 / 设计 / 创业者** → 路径 B
4. **是开发者 / 有协作开发经验** → 路径 B

## 两条路径的差异

**路径 A（小白）：**
- 大白话，避免 user story / sitemap / 漏斗 / KPI 这些术语
- 每个问题给具体选项 + 示例
- 信息架构问题用"这个页面打开后，从上到下应该看到什么？"这种自然语言

**路径 B（有经验）：**
- 允许产品 / 工程语言
- 信息架构可以直接用"区块"概念问

两条路径问到的"本质信息"一致。

## Step 2：分批问问题

### 批 1：本次目标 + 基线（首次 vs 迭代分支不同）

**首次分支**（v1-launch）：

1. **项目背景确认**——基于 BRIEF 知道项目是什么、给谁、长期价值。让用户简短确认或补充："BRIEF 里说 X，第一版做出来后，主要场合 / 用途是什么？"
2. **本次（第一版）的核心目标**——上线后让用户能完成的 1-2 件最重要的事
   - 区别于 BRIEF 的"长期成功"。PRD 目标是**可在第一版上线就开始验证**的具体目标
   - 路径 A 选项：让陌生人看到我的作品并能联系我 / 卖出第一单 / 收集前 100 个邮件订阅者 / 把内容搬上线建立公开身份 / 其他
   - 路径 B：直接让用户描述

**迭代分支**（v2+）：

1. **回顾上一版**——基于读到的上一份 PRD，简短复述：「上一版做了 X，目标是 Y，从 plan 看实际做完的功能是 Z」让用户确认或补充偏差
2. **本次迭代的核心目标**——这次要解决什么新问题 / 加什么新能力？
   - 强调：**本次目标必须落在 BRIEF 边界内**。如果用户提的需求和 BRIEF "永远不会做" 冲突 → 停下确认"这是不是要改 BRIEF？还是收窄需求？"
   - 路径 A 选项：加新内容类型（如博客 / 案例）/ 加新交互（如评论 / 订阅）/ 改首版没做好的体验 / 扩展到新受众 / 性能 / SEO 优化 / 其他
   - 路径 B：直接让用户描述
3. **本次迭代的范围边界**——要明确"本次只做哪些，不做什么"——这是迭代防 scope creep 的关键
   - 比首次更重要——首次还能容忍 scope 稍大，迭代必须聚焦

### 批 2：用户与关键场景

不要单独列"用户画像"再列"场景"——**把用户描述嵌进每个场景里**，让阅读 PRD 的 AI 能直接看到"谁 + 在什么背景下 + 做什么"。

要问到的事：

1. **3-5 个核心场景**。每个场景包含：
   - **用户**：身份 + 来到网站的背景（如"中小品牌创始人，通过同行推荐听说 Linka"）
   - **旅程**：从 X 到 Y 的关键动作（如"点链接 → 看首页风格 → 点 1-2 个作品 → 通过联系表单留需求"）
   - **结果**：旅程结束时希望发生的事（如"留下联系方式"或"加书签下次再来"）

询问技巧：
- 路径 A 问："想象一下：第一个真的会用上这个网站的人，他从哪里听说你，进网站后会做什么，离开时希望发生什么？"
- 路径 B 问："列 3-5 个第一版要覆盖的关键用户旅程，每个旅程谁、从哪里来、做什么、目标"

### 批 3：页面结构 + 信息架构

**这是 PRD 的核心。先问页面结构，再问每个页面的信息架构。**

#### 3.1 页面结构

问：第一版要做哪些页面？每个页面用一句话讲清楚干什么。

- 路径 A 选项（多选）：首页 / 关于我 / 关于公司 / 作品列表 / 作品详情 / 文章列表 / 文章详情 / 产品介绍 / 定价 / 联系 / 注册登录 / 隐私政策 / 其他
- 路径 B：直接让用户列路由 + 一句话用途

结果整理成：
```
- `/`           首页 —— ...
- `/about`      关于 —— ...
- `/works`      作品列表 —— ...
- `/works/[id]` 作品详情 —— ...
```

#### 3.2 信息架构

**对每个核心页面**，问"这个页面从上到下要有哪些区块？每个区块的用途是什么？要放什么类型的内容（内容槽）？"

每个区块要拿到三件事：
- **区块名**（如 Hero 区、核心介绍区、作品网格区、CTA 区）
- **用途**（一句话，"做什么用的"）
- **内容槽清单**（这个区块需要哪些具体的内容碎片，**给后续 CONTENT.md 用**）

格式示例：
```
### 首页 `/`
- **Hero 区** —— 第一屏抓住注意，传达定位。
  - 内容槽：slogan(1 句) / 副文案(1-2 句) / 主 CTA 按钮(文字 + 链接) / 主视觉图
- **差异化介绍区** —— 解释为什么选我 / 这个产品。
  - 内容槽：3-4 个差异点 / 每个差异点配 1 句简述 + 配图（图位）
- **联系区** —— 引导留下联系方式。
  - 内容槽：一句话引导文案 / 联系表单字段清单
```

**自适应粒度**：
- 简单项目（≤ 4 个页面）：每个页面 3-6 个区块，每个区块 2-4 个内容槽
- 复杂项目：可以更细，但**不要进入 UI 细节**（颜色 / 字体 / 间距 / 动效都属于 DESIGN）

**拦截规则**：
- 用户说"按钮要蓝色 / 字体用 Inter / 卡片用阴影" → 拉回："这些视觉细节我们写进 DESIGN.md，PRD 只关心'这个位置放什么类型的内容、用什么用途'"
- 用户说"用 Next.js / Supabase / Cloudflare" → 拉回："技术选型放进 ARCHITECTURE.md"
- 用户说"slogan 是 'Build faster with AI'" → 回应："这具体文案我们留给 CONTENT.md。PRD 这里只标 '内容槽：slogan(1 句)'。"

### 批 4：目标衡量 + 范围

#### 4.1 目标衡量（漏斗指标 + 主指标）

要拿到的事：

1. **主指标（North Star）**——上线后 30-90 天达成的最终目标。1-2 条，必须可验证。
2. **漏斗指标（过程指标）**——从用户到达到最终转化中间的每一步。问"主指标"达成前，用户要走过哪几个关卡？

举例（个人作品集）：
- 主指标：90 天内通过联系表单收到 ≥ 5 份认真合作咨询
- 漏斗：到达首页 → 浏览作品（看 2+ 件）→ 进入联系页 → 提交表单 → 邮件回复

举例（SaaS 落地页）：
- 主指标：30 天首页 → 注册转化 ≥ 5%
- 漏斗：到达首页 → 滚动到 CTA 区 → 点 CTA → 完成注册

询问技巧：
- 路径 A：先问"上线后 3 个月你希望发生什么事？" → 再问"从用户第一次打开网站到那件事发生，中间会经过哪几步？"
- 路径 B：直接问 main metric + funnel

#### 4.2 范围（这一版做 / 不做）

1. **这一版会做**——前面已经定的页面 / 功能合集，一句话清单
2. **这一版明确不做**——常见 scope creep 项要主动提示：
   - 用户系统 / 登录注册（除非业务必须）
   - 评论 / 互动
   - 多语言
   - 复杂动效
   - 移动 App
   - 后台 / CMS
   - 分析 dashboard
   提示用户："凡是这一版用不上的，写到不做里。等真的要做时再起新的 PRD。"

## Step 3：预填风险与待解决问题

**这是 PRD 末尾的"风险与待解决问题"章节。skill 主动预填常见项**（按用户的网站类型挑选），同时**留出明显的"请补充"区**。

常见项库（按需挑 2-4 条）：

- 域名是否已注册 / 选好
- 邮件 / 表单服务未定（候选：Resend / SendGrid / Postmark / Formspree）
- 部署平台未定（候选：Vercel / Netlify / Cloudflare Pages）
- 内容素材是否完备（文字、图片、作品图等）
- SEO 元信息（meta description、OG image）谁来写
- 反垃圾 / 反爬机制（hCaptcha / Turnstile / honeypot）
- 数据分析工具未定（GA / Plausible / Umami）
- 第三方依赖的账号和密钥
- 法务页（隐私政策 / 服务条款）的措辞

预填完后，PRD 末尾要明显写一行：

```
**👇 请在这里补充你自己项目独有的风险或待解决问题（skill 不知道但你知道的）：**
- 
- 
- 
```

写完文件后，在对话里也明确告诉用户："PRD 已经写好。我在'风险与待解决问题'里预填了 X 条常见项，**请你回头补上你自己项目独有的那些**——比如内部依赖、合作方进度、合规要求、特殊用户群等等，我不知道的。"

如果文件已存在，对比后让用户确认是否覆盖。Cowork 环境写到 outputs 并给 `computer://` 链接。

## 写作风格守则

- 用陈述句，避免"可能 / 也许 / 之后再说"
- 信息架构写"区块名 + 用途 + 内容槽"，**不写视觉**（颜色 / 字体 / 间距）、**不写技术**（框架 / 库）、**不写具体文案**（具体文案归 CONTENT.md）
- 用户场景必须包含"谁、为什么来、做什么、结果"四要素
- 漏斗指标的每一步必须**可观测**——能从 GA / Plausible / 后端日志看到的步骤
- 主指标必须**可验证**且带时间窗口
- 范围里的"不做"必须真的写出来——这是 PRD 防 scope creep 的关键
